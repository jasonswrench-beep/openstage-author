## Phase 7: what to do next

Read `docs/decisions/0003-steps-and-practice.md` first. In short: OS-12, OS-13 and OS-14 were already done in format 0.18.0 (`setVariable` add, the
`hotspot` object, `provenance` for a capture step), and typing and scoring are covered by the quiz kinds `shortAnswer` and `hotspot`, so **no new format
is needed**. Stages, in order:

1. **Pictures.** A picture beside each step in the dialog, grabbed in the window from the take's video: a `<video>` with `crossOrigin = "anonymous"`,
   seek to `shotMs`, draw on a canvas, `toBlob("image/png")`. **Verified 2026-10-16 on a synthetic 640 by 360 recording; without `crossOrigin` the canvas is
   tainted and export is refused.** A real recorder file (a fragmented MP4) has not been tried. The target is a place in the picture (steps keep it in
   picture pixels; the log has a click point and a name, not the element's outline, so start with a box centred on the click that the author can move and
   resize). Needs a new shell command to save a PNG in `assets/images` (copy the pattern of `save_deck_picture_at`: check the PNG's first bytes, a safe name).
2. **Demo slides.** One slide per step: picture, marked target, words, narration made from the words (this is the audio route for step text, story D7),
   `provenance: { sourceCapture: <recording folder name>, stepId }` on the slide, alt text **only from steps the author ticked as checked** (`reviewed`),
   inserted at a position the author chooses. Slides are built with the factory functions in `editor/src/factory.ts` and `Model` methods.
3. **Practice**, 4. **Assessment**, 5. **bring the lesson up to date** when steps change, as in the ADR.

**Jason must choose** (put it to them plainly when you reach Stage 3 or 4): for Practice, hotspot objects over the picture (feels like the real program;
needs layers and an attempts variable) or the quiz hotspot question (scored by existing machinery, less like the real thing). The ADR recommends hotspot
objects for Practice and the quiz kinds for Assessment, because only quiz objects add to the score.

## Traps found in this stretch (add to the list in `HANDOFF.md`)

- **This environment's bash tool collapses double backslashes in heredocs** (a Python `"\\n"` became a real newline in the file). Write patch scripts with the
  file-writing tool, use raw strings, or build backslashes with `chr(92)`. Heredocs are fine for text with no backslashes.
- Many tracked files are CRLF in the working tree (`editor/src/app.ts`, `editor.css`, `ROADMAP.md`, `docs/editor.md`, `docs/capture/roadmap.md`); patch
  scripts must read with `newline=''`, replace on LF text and write the original endings back. Git Bash `grep` cannot see CR.
- The edit tool refuses a file you have not read in this conversation, and refuses if the file changed since. Read it again.
- `rm -rf "$VAR"` is refused by the safety check; use a literal path or a fresh name.
- Recorder tests with cue sounds on make real beeps on Jason's PC. Use `--cues off` (the Rust test for it is already fixed) and do not run
  `cues_on_or_off` casually.
- A crash-recovery Rust test flaked twice in about 40 Windows runs and never again in about 26 silent runs; it now names the leftover file. Not
  understood. Watch for it.
- Web fetches of a page are summarised by a small model and can be wrong about a licence. Check a licence against the project's own LICENSE file and the
  package or model listing's API (`api.github.com`, `huggingface.co/api/models/...`, `pypi.org/pypi/<name>/json`).
- A `<video>` drawn to a canvas from the app's asset address needs `crossOrigin = "anonymous"` or the export is blocked.
- Do not use `Edit` on a very large replacement with backslashes; use a patch script.
- New **Rust commands** must be added to the `invoke_handler` line in `lib.rs`; a new `Backend` method must be added to the interface, to the Tauri
  backend, and to the web stub in `editor/src/backend.ts`.
- A dialog resolves with a message string that the caller says; if the dialog is opened from inside another modal dialog (the recording editor), say it
  in that dialog's own status line, because the editor's live region sits behind the modal and may not be heard.

## Driving the real desktop app (how this stretch was verified)

1. Build: in `editor/`, `npm run build`, then `npx tauri build --no-bundle` (close the app first; about 35 seconds).
2. Launch `editor/src-tauri/target/release/openstage-editor.exe` with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` and
   `OPENSTAGE_PYTHON=python`.
3. Drive the page over the Chrome DevTools protocol: a ten-line Node script that fetches `http://127.0.0.1:9222/json`, opens a WebSocket to the page,
   and sends `Runtime.evaluate` with `awaitPromise`; the script under test is plain JavaScript run in the page (it clicks buttons by their text, waits for
   words in status lines, and returns a PASS or FAIL list). `Page.captureScreenshot` gives a PNG to look at.
4. Native file pickers cannot be driven; set `window.__openstageTestPick = (kind) => path` (kinds: `open`, `new`, `publish`, `captionsource`, and the asset
   kinds). A scratch course with a made-up recording is enough: a folder with `project.json`, `theme.json`, `slides/`, and `captures/Sample.capture/` holding
   `capture.json`, `takes/take-001/{take.json, screen.mp4, mic.wav, events.jsonl}`.
5. Native confirm dialogs cannot be driven; avoid paths that confirm, or restart the app.

These scripts were in a session scratchpad and are **not** in the repository. A future instance could add the small driver and the made-up-recording
builder to a `tools/` folder, with a `.bat` to run them; that would be worth doing before the next big feature.
